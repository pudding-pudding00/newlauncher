# M7 – Hardware-Abnahme: Implementierungsplan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** M0–M6 laufen nachweislich auf einer echten Wii mit USB-Platte. Die Performance-Budgets aus Spec §7 sind gemessen, jeder Befund ist mit Test behoben.

**Architecture:** Der Launcher misst sich selbst. Mit `[debug] perf = 1` schreibt er `NL_PERF`-Zeilen ins Log, das auf der Wii in `sd:/newlauncher/log.txt` landet.
- Die Auswertung (Fenster, Perzentile, Formatierung) liegt host-getestet in `core/perf_stats`.
- `tools/check_perf.py` liest die Logdatei vom PC aus und prüft die Budgets.
- `tools/wii_deploy.py` bringt Build, `dist/` und optional die Fixture-Bibliothek auf die SD-Karte.
- `docs/hardware-acceptance.md` ist die Checkliste: Der Nutzer arbeitet sie an der Wii ab, der Agent wertet aus und behebt Befunde.

**Tech Stack:** wie M6. Neu: Python 3 (Standardbibliothek) für die Werkzeuge, `wiiload.exe` aus `C:\devkitPro\tools\bin` (vorhanden).

**Spec:** `docs/superpowers/specs/2026-11-09-wii-launcher-design.md`, Abschnitte:
- §1.1 (Rahmenbedingungen), §3.10 (Video)
- §6.1 (Startablauf, Splash < 0,5 s), §7 (Performance-Budgets)
- §8.4 (`wiiload` ab M7), §9 M7
- §10 (Risiken: `argv`-Schema der Emulatoren, Bannernamen, Messbarkeit in Dolphin)

**Basis:** Branch `feat/m7-hardware` von `main` nach dem Merge von M6.

## Global Constraints

- Alle Global Constraints aus M1–M6 gelten weiter.
- Budgets aus Spec §7, wörtlich:

  | Kriterium | Budget |
  |---|---|
  | Start bis bedienbar (Cache vorhanden, ohne USB-Anlaufzeit) | ≤ 2 s |
  | Bildrate beim Scrollen und bei Animationen | konstant 60 fps (PAL50: 50 fps) |
  | Sichtbares Cover aus Cache bis Anzeige | ≤ 100 ms |
  | Heap-Allokationen im Render-Loop | 0 |
  | Blockierung der UI durch Scan oder Download | keine |

- Messung nur mit `[debug] perf = 1`. Ohne den Schlüssel ändert sich am Verhalten und am Log nichts.
- Perf-Marker, exaktes Format (Zahlen ohne Einheit, ms mit einer Nachkommastelle, wo angegeben):
  - `NL_PERF boot first_frame_ms=<n> ready_ms=<n> usb_wait_ms=<n> hz=<50|60>`: einmal nach `NL_READY`
  - `NL_PERF frames n=<n> slow=<n> max_ms=<x.y> busy=<0|1>`: alle 300 Frames ab `NL_READY`. `busy=1`, wenn im Fenster Scan, Cover-Download oder Cover-Umwandlung lief.
  - `NL_PERF summary ready_ms=<n> usb_wait_ms=<n> hz=<n> frames=<n> slow=<n> max_ms=<x.y> cover_n=<n> cover_p50=<x.y> cover_p95=<x.y> cover_max=<x.y> mem1_free=<bytes> mem2_free=<bytes> heap_free=<bytes>`: vor jedem Log-Flush beim Spielstart und beim Beenden
- Kein Werkzeug schreibt ungefragt über Daten des Nutzers:
  - `config.ini`, `emulators.ini`, `favorites.ini`, `history.ini`, `n64_vc.ini`, `games.ini` und `cache/` werden nie überschrieben.
  - `config.ini`/`emulators.ini` werden nur aus `dist/` angelegt, wenn sie fehlen.
- Die Abnahme läuft gegen die **Release-DOL** `newlauncher.dol`. Die Selbsttest-DOL läuft nur auf einer eigenen, leeren SD-Karte (siehe Task 4).

## Review Focus

1. **`log.txt` ist ein 16-KB-Ringpuffer:** In langen Sitzungen fallen `NL_PERF boot` und frühe Fenster heraus. Erwartet: `NL_PERF summary` enthält alle Budget-Werte. `check_perf.py` urteilt allein aus der letzten Summary und meldet fehlende Fenster nur als Hinweis (Task 3).
2. **PAL50 und 60 Hz:** Ein langsamer Frame ist relativ zur Bildwiederholrate definiert. Erwartet:
   - bei 50 Hz gelten 20-ms-Frames nicht als langsam, bei 60 Hz gilt ein 34-ms-Frame als langsam
   - `check_perf` nennt das Budget passend zu `hz=` (Task 1, Task 3)
3. **SD-Karte voll, schreibgeschützt oder falscher Laufwerksbuchstabe:** Erwartet: `wii_deploy.py` bricht mit klarer Meldung und Exit-Code 2 ab, bevor irgendetwas kopiert wird. Beispiel: Laufwerk ohne `apps/` und ohne `--init` → „kein Wii-SD-Laufwerk?“ (Task 4).
4. **Platte schläft oder läuft langsam an (länger als `usb_timeout`):** Erwartet:
   - Die Anlaufzeit steht in `usb_wait_ms` und zählt nicht ins Startbudget.
   - Der Dialog „Erneut versuchen“ / „SD verwenden“ erscheint.
   - Die Checkliste prüft beides ausdrücklich (Task 5).
5. **Deploy auf eine Karte mit echter Bibliothek:** Erwartet:
   - Ein normaler Deploy lässt alle Nutzerdateien stehen.
   - `--selftest` verweigert eine Karte mit `wbfs/`, `games/`, `roms/` oder `newlauncher/` mit Exit-Code 2.
   - Fixture-Dateien landen nie neben echten Spielen (Task 4).

## Abweichungen und Festlegungen gegenüber der Spec

| Punkt | Festlegung in M7 | Grund |
|---|---|---|
| „Start“ im Startbudget | Zeit ab Eintritt in `main()` bis `NL_READY`, abzüglich `usb_wait_ms` | Die Ladezeit des HBC ist von innen nicht messbar und nicht Teil des Launchers |
| „Konstant 60 fps“ | Ein Frame ist langsam, wenn sein Abstand zum vorigen > 1,5 × Periode ist (60 Hz: > 25,0 ms; 50 Hz: > 30,0 ms). Budget: `slow = 0` über die ganze Sitzung ab `NL_READY` | Ein ausgelassener VSync verdoppelt den Abstand; 1,5 trennt sauber von Messrauschen |
| Cover-Budget | Gemessen ab dem ersten `want(Visible)` bis zum Eintreffen der Texel, **nur für `.tex`-Ladevorgänge** (PNG-Umwandlung ist der Erstfall, nicht „aus Cache“). Grenze: `cover_p95 ≤ 100 ms`. `cover_max > 250 ms` ergibt WARN, kein FAIL | Ein einzelner langsamer SD-Zugriff soll nicht die ganze Abnahme kippen. **Der Nutzer bestätigt diese Lesart beim Plan-Review.** |
| Allokationen im Render-Loop auf Hardware | über die Selbsttest-DOL auf einer eigenen SD-Karte (`NL_ALLOC_IDLE 0`) | Der Zähler existiert nur im Selbsttest-Ziel. Die Release-DOL bleibt ohne `--wrap` |
| Logausgabe auf Hardware | nur über `sd:/newlauncher/log.txt` (Flush bei `NL_READY`, Spielstart, Beenden) | `SYS_Report` ist auf echter Wii ein No-op (`platform/log.hpp`) |
| Nintendont/Wii-Spiele | in M7 nur Voraussetzungen erfassen (Nintendont-Version, cIOS, Plattenformat) | Die Backends kommen mit M8/M9; ihre Pläne brauchen diese Daten |

### Task 3: `tools/check_perf.py`

**Files:**
- Create: `tools/check_perf.py`, `tools/tests/test_check_perf.py`

**Interfaces:**
- Consumes: Markerformat aus den Global Constraints
- Produces:
  - `parse_log(text: str) -> PerfLog`; `PerfLog` ist eine Dataclass:
    - `boot: dict | None`
    - `windows: list[dict]`
    - `summary: dict | None` (letzte Summary)
    - `alloc_idle: int | None` aus `NL_ALLOC_IDLE <n>`
  - `evaluate(log: PerfLog) -> list[Check]`; `Check(name, value, budget, status)` mit `status ∈ {"PASS", "WARN", "FAIL", "N/A"}`:
    - **Start:** `ready_ms − usb_wait_ms ≤ 2000`
    - **Bildrate:** `slow == 0` (Budget-Text `60 fps` bzw. `50 fps` nach `hz`)
    - **Cover:**
      - `cover_p95 ≤ 100` → PASS
      - zusätzlich `cover_max > 250` → WARN
      - `cover_n == 0` → N/A
    - **Blockierung:** alle Fenster mit `busy=1` haben `slow=0`; FAIL nennt die Nummern der Fenster
    - **Allokationen:** `alloc_idle == 0`; fehlt der Wert → N/A mit Hinweis „Selbsttest-Karte“
    - **Splash** (Spec §6.1, Ziel): `first_frame_ms ≤ 500` → sonst WARN, nie FAIL
  - CLI:
    - `python tools/check_perf.py <log.txt> [<weitere log.txt>]`: mehrere Dateien werden zusammengeführt, z. B. Release-Log und Selbsttest-Log
    - druckt eine Markdown-Tabelle (zum Einfügen in `docs/hardware-acceptance.md`)
    - Exit 0 bei PASS/WARN/N/A, 1 bei mindestens einem FAIL, 2 ohne `summary` in allen Dateien
