# M9 – Wii nativ: Implementierungsplan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wii-Spiele aus `wbfs/` (`.wbfs` samt `.wbf1…`, `.iso`) starten direkt. Der Launcher berechnet die Fragmentliste der Spieldatei, lädt d2x-cIOS 249 und übergibt an den portierten Game-Booter. Der Booter emuliert die Disc, führt den Apploader aus und setzt die Patches für Videomodus und Sprache.

**Architecture:**
- `boot/` ist ein eigenes Programm: ein Port des Game-Boot-Codes aus WiiFlow Lite (`resources/wiiflow_game_booter`, GPLv3+), gelinkt ab `0x80A80000`.
  - Es wird als DOL gebaut und wie der M3-App-Booter über `dkp_add_embedded_binary_library` in `newlauncher.dol` eingebettet.
  - Der Start läuft über den bestehenden Chainloader aus M3. Der Stub bei `0x93300000` kopiert die Sektionen nach MEM1, genau wie WiiFlows `ext_loader`.
- Die Konfiguration (`the_CFG`) und die Fragmentliste liegen an festen Adressen im reservierten MEM2-Bereich. Der Booter liest sie dort direkt, statt wie upstream über einen Zeiger bei `0x90100000`: Diese Adresse liegt im MEM2-Heap des Launchers.
- Die Fragmentliste entsteht vollständig vor dem IOS-Reload, host-getestet in `core/`:
  - `fat_chain`: MBR und BPB lesen, Clusterkette ablaufen
  - `wbfs_map`: Disc-Blöcke → Dateioffsets, Split-Dateien
  - `frag_list`: zusammensetzen, verschmelzen, Big-Endian serialisieren
- Die Plattform liefert nur Rohsektoren und den Startcluster. Vor dem Start prüft sie die Liste gegen das Dateisystem (erster und letzter Sektor).

**Tech Stack:** wie M8. Neu: Quellcode des WiiFlow-Lite-Game-Booters (GPLv3-or-later, FIX94 u. a.; mit der GPLv3 dieses Repos verträglich), `elf2dol` aus devkitPPC.

**Spec:** `docs/superpowers/specs/2026-11-09-wii-launcher-design.md`, Abschnitte:
- §1 (Wii-Spiele), §1.1 (d2x-cIOS 249)
- §4.1 (`boot/`), §5.1 (`wbfs/<Titel> [ID6]/<ID6>.wbfs`)
- §6.2 (Wii-Scanner, Split-Dateien), §6.5 (Backend `WiiDisc`, Preflight „cIOS vorhanden, Spieldatei lesbar“)
- §9 M9

**Basis:** Branch `feat/m9-wii-nativ` von `main` nach dem Merge von M8.

## Global Constraints

- Alle Global Constraints aus M1–M8 gelten weiter.
- **Upstream:**
  - Repo `https://github.com/Fledge68/WiiFlow_Lite`, Pfad `resources/wiiflow_game_booter/`
  - Commit wird in Task 1 auf den aktuellen `master` festgelegt und in `boot/UPSTREAM.md` notiert, zusammen mit Lizenz, Autoren und jeder Änderung als Liste
  - Dateien behalten ihre Lizenzköpfe
- **Speicher:**

  | Adresse | Inhalt |
  |---|---|
  | `0x80A80000` | Ladeadresse des Booters (`.init`) |
  | `0x92800000` | Booter-DOL im bestehenden DOL-Puffer |
  | `0x93200000` | `the_CFG` (`kWiiCfgAddr`) |
  | `0x93201000` | Fragmentliste (`kFragListAddr`), immer die volle Größe 12 + 20000 × 12 = 240 012 Byte, Rest 0 |

  - Beide liegen im DOL-Puffer `[kDolBufferAddr, kBooterAddr)` (`src/core/launch_layout.hpp`, 11 MiB) hinter dem Booter. Der Booter-DOL darf deshalb höchstens `0x93200000 − 0x92800000` = 10 MiB groß sein.
  - Der Launcher schreibt **nichts** nach `0x90100000`.
  - Der M3-Stub beschreibt nur die Ziel-Sektionen und das BSS (`src/launch/app_booter/booter.c`). CFG und Liste bleiben also bis zum Booter erhalten.
- **Fragmentliste**, Format upstream (`FragList`/`Fragment`), Big-Endian, Einheit 512-Byte-Sektor:
  - Kopf: `u32 size`, `u32 num`, `u32 maxnum = 20000`
  - je Eintrag: `u32 offset` (Disc-Offset), `u32 sector` (LBA auf dem Gerät), `u32 count`
  - Einträge nach `offset` sortiert; benachbarte Einträge, die in Offset und LBA lückenlos sind, werden verschmolzen
  - mehr als 20000 Einträge → Fehler
- **Unterstützte Dateisysteme:** FAT32 mit 512-Byte-Sektoren, auf USB (erstes gültiges FAT-Volume wie libfat) und SD. Alles andere → Dialog „Dateisystem nicht unterstützt“.
- **FAT-Typ** nach Clusterzahl (Microsoft-Regel): < 4085 FAT12, < 65525 FAT16, sonst FAT32.
- **WBFS-Datei:**
  - Magic `WBFS`, `hd_sec_sz_s` = 9, `wbfs_sec_sz_s` aus dem Kopf
  - Disc-Info ab Byte 512, `wlba_table` (BE-u16) ab Byte 512 + 0x100
  - `n_wbfs_sec_per_disc = (143432 × 2) >> (wbfs_sec_sz_s − 15)`
  - Block `i` mit `wlba ≠ 0` liegt ab Disc-Offset `i × wbfs_sec_sz` und ab Dateioffset `wlba × wbfs_sec_sz`
  - Split-Teile `.wbf1`, `.wbf2`, … (höchstens 9); Split-Größe = Größe der ersten Datei, sobald `.wbf1` existiert
- **`.iso`:** Disc-Offset = Dateioffset.
- **`size`** der Liste:
  - ISO: `ceil(Dateigröße / 512)`
  - WBFS: Ende des letzten Fragments
  - Task 1 gleicht das gegen upstream `frag.c` ab und hält es in `UPSTREAM.md` fest.
- **cIOS:**
  - Slot 249, `iosinfo_t`: Magic `0x1EE7C105`, `magicversion = 1`, Felder `version`, `baseios`, `name[16]`, `versionstring[16]`
  - d2x, wenn `name` mit `d2x` beginnt
- **`the_CFG`**, Standardwerte; alles andere 0 bzw. `nullptr`:

  | Feld | Wert |
  |---|---|
  | `BootType` | `TYPE_WII_GAME` |
  | `GameBootType` | `TYPE_WII_WBFS_EXT` |
  | `gameID` | ID6 |
  | `fragments` | `kFragListAddr` |
  | `wbfsDevice` | upstream-Konstante für USB bzw. SD |
  | `wbfsPart` | 0 |
  | `vidMode` | `1` (System, laut `Disc_SelectVMode`) |
  | `patchVidMode` | 0 |
  | `configbytes` | `{0xCD, 0xCD}` (nicht gepatcht: Spiel nutzt Systemsprache) |
  | `aspectRatio`, `deflicker`, `videoWidth` | „Spielstandard“ laut upstream |
  | `IOS` | aus `iosinfo_t` (Version 249, Basis, Typ d2x) |
  | `JustDanceGame` | Regel aus WiiFlow Lite, in Task 1 mit Quellzeile übernommen |
  | `returnTo` | 0 |

  Keine Cheats, kein Ocarina, keine WIP-Patches, kein Debugger.
- **Neue Marker:**
  - `NL_CIOS ok base=<n> ver=<s>|unverified|missing|not_d2x`
  - `NL_FRAG dev=<sd|usb> part_lba=<n> n=<count> size=<sectors> crc=<crc32 hex> first=<off>:<lba>:<cnt>`
  - `NL_FRAG_VERIFY ok|fail <welcher Sektor>`
  - `NL_WII_DRYRUN <id6>`: nur mit `[debug] wii_dry_run = 1`
  - `NL_IOS_RELOAD 249`

## Review Focus

1. **Dateisystem-Randfälle:**
   - Partition nicht an erster Stelle, Karte ohne MBR, GPT-Platte (Schutz-MBR `0xEE`), 4K-Sektoren, exFAT/NTFS, FAT16-SD unter 2 GB
   - Erwartet: Jeder Fall endet mit einem klaren Dialog, nie mit einem Start auf falschen Sektoren (Task 2, Host-Tests je Fall).
2. **Kaputte oder extreme Clusterketten:**
   - Schleife, vorzeitiges Ende, freier Cluster mitten in der Kette, mehr als 20000 Fragmente
   - Erwartet: Fehler in begrenzter Zeit (höchstens so viele Schritte wie Cluster der Datei plus eins), kein Hänger, kein Speicherüberlauf (Task 2, Task 3).
3. **Split-WBFS:**
   - Block über der Split-Grenze, `.wbf1` fehlt, Split-Größe kein Vielfaches der Clustergröße
   - Erwartet: korrekte Abbildung über beide Teile bzw. Fehler „Spieldatei unvollständig“ (Task 3).
4. **Annahme zum Startcluster bricht** (`st_ino` von libfat ist nicht der Startcluster, oder ein anderes Volume ist gemountet).
   Erwartet:
   - Die Prüfung von erstem und letztem Sektor (roh gelesen gegen Dateisystem) schlägt an.
   - Dialog statt Start.
   - Der Dolphin-Probelauf gleicht zusätzlich mit einem unabhängigen Python-Parser ab (Task 5).
5. **Fehler nach dem Punkt ohne Rückkehr** (IOS-Reload scheitert, Booter hängt). Erwartet:
   - `log.txt` ist vor dem Abbau geschrieben (inklusive `NL_FRAG`, `NL_CIOS`).
   - Scheitert der Reload, folgt die Rückkehr ins Wii-Menü.
   - Alles Prüfbare steht im Preflight: cIOS-TMD vorhanden, Liste verifiziert (Task 4–6).

## Abweichungen und Festlegungen gegenüber der Spec

| Punkt | Festlegung in M9 | Grund |
|---|---|---|
| Inhalt von `boot/` | Port des WiiFlow-Lite-Game-Booters statt Eigenbau | bewährter Code für Apploader, Disc-Emulation und Patches; GPLv3+ passt zum Repo |
| Übergabe an den Booter | über den M3-Chainloader (Booter als DOL), nicht über WiiFlows `ext_loader.bin` | gleicher Mechanismus, ein Stub weniger |
| CFG-Adresse | Der Booter liest `the_CFG` fest bei `0x93200000`, nicht über den Zeiger bei `0x90100000` (Änderung in `UPSTREAM.md`) | `0x90100000` liegt im MEM2-Heap des Launchers; ein Schreibzugriff vor dem Abbau könnte Malloc-Metadaten zerstören |
| Fragmentliste | eigener FAT32-Parser über Rohsektoren und den Startcluster aus `stat().st_ino`, statt `_FAT_get_fragments` (nur in WiiFlows libfat-Fork) | Stock-libfat aus devkitPro reicht; der Parser ist host-testbar |
| Dateisysteme | nur FAT32 mit 512-Byte-Sektoren; NTFS, exFAT, WBFS-Partitionen und 4K-Sektoren → Dialog | Spec §5.1 sieht Dateien unter `wbfs/` vor; mehr ist v2 |
| cIOS-Prüfung | TMD von IOS 249 muss existieren. `iosinfo_t` wird gelesen, wenn ISFS es unter IOS 58 erlaubt; sonst `NL_CIOS unverified`, Start mit der Annahme d2x (Basis aus M7-V3, sonst 56) | Spec §1.1 setzt d2x-cIOS voraus; ein Leseverbot soll den Start nicht verhindern |
| Patches | nur Standard: Videomodus „System“, Sprache ungepatcht. Keine Spieloptionen, keine Cheats | Spec §6.5 nennt Videomodus und Sprache; Optionen sind v2 |
| Dolphin-Abnahme | nur Probelauf (`[debug] wii_dry_run = 1`): Preflight und Fragmentliste ohne Reload. Abgleich gegen `Load/WiiSD.raw`. Ist das Image kein FAT32, wird das als Ruling notiert und der Abgleich entfällt | Dolphin hat kein cIOS 249; der Start selbst ist nur auf der Wii prüfbar |

### Task 2: FAT32-Kette

**Files:**
- Create:
  - `src/core/block_dev.hpp`, `src/core/fat_chain.hpp/.cpp`
  - Test: `tests/host/core/fat_chain_test.cpp`, `tests/host/support/fat_image.hpp`

**Interfaces:**
- Produces:
  - `struct BlockDevice { virtual ~BlockDevice() = default; virtual bool read(u32 lba, u32 count, std::span<u8> out) = 0; virtual u32 sectorSize() const = 0; };`
  - `enum class FatError : u8 { Io, SectorSize, NoFatVolume, NotFat32, BadChain, ChainTooShort }`
  - `struct FatVolume { u32 partLba, fatLba, dataLba, sectorsPerCluster, clusterCount; }`
  - `Result<FatVolume, FatError> findFatVolume(BlockDevice&)`:
    - `sectorSize() != 512` → `SectorSize`
    - Sektor 0 ist ein gültiger FAT-Bootsektor (`0x55AA`, Bytes pro Sektor 512, Sektoren pro Cluster ∈ {1, 2, 4, …, 128}, FAT-Anzahl ≥ 1) → Volume ab 0
    - sonst die vier primären MBR-Einträge in Reihenfolge, erster mit gültigem Bootsektor; keiner → `NoFatVolume`
    - FAT-Typ nach Clusterzahl; nicht FAT32 → `NotFat32`
  - `struct Extent { u32 fileSector, lba, count; }`: `lba` ist absolut auf dem Gerät (`partLba` eingerechnet)
  - `Result<std::vector<Extent>, FatError> fileExtents(BlockDevice&, const FatVolume&, u32 startCluster, u64 fileSize)`:
    - folgt der Kette, bis `ceil(fileSize / clusterBytes)` Cluster beisammen sind, und verschmilzt lückenlose Cluster
    - Wert `< 2`, `0x0FFFFFF7` (bad) oder Kettenende zu früh → `ChainTooShort` bzw. `BadChain`
    - FAT-Sektoren mit einem Ein-Sektor-Cache lesen
    - Einträge mit `& 0x0FFFFFFF` maskieren
  - Testhilfe `fat_image.hpp`:
    - `SparseDisk : BlockDevice`: nur beschriebene Sektoren im Speicher, sonst Nullen, einstellbare Sektorgröße
    - `Fat32Builder(SparseDisk&, u32 partLba, u8 sectorsPerCluster, u32 totalSectors)`:
      - schreibt MBR (Typ `0x0C`) und BPB
      - `setChain(std::vector<u32>)` trägt eine Kette in die FAT ein
      - `clusterLba(u32)` liefert die LBA eines Clusters
      - Variante ohne MBR
